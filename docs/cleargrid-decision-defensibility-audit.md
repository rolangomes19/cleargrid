# Decision & Metric Defensibility Audit — ClearGrid Case Study

Third document in the set. Give this to Claude Code alongside `cleargrid-case-study-brief.md` and `cleargrid-agent-journey-expansion.md`. This one exists for one reason: the product lead's feedback was "every decision has to be deliberate and defensible, every metric has to be accounted for." This audits the existing material against that exact bar and fixes what fails it.

---

## 1. The standard, made concrete

"Defensible" is not a feeling. It's a checkable claim. Two ledgers, both mandatory in the finished case study:

**Decision ledger** — every named design decision gets four fields, not a paragraph of prose:

| Field | What it answers |
|---|---|
| Decision | What was chosen |
| Evidence | What fact, source, or measurement justifies it |
| Alternative rejected | What else was considered and why it lost |
| Confidence | High / Medium / Low — say so plainly when evidence is thin |

**Metric ledger** — every number that appears anywhere in the case study gets tagged as exactly one of:

| Tag | Meaning | Example |
|---|---|---|
| **External fact** | Sourced to a named, linked, outside source | "ClearGrid claims 38–50% better resolution rates (Dealroom)" |
| **Live-computed** | Generated by the prototype itself, reproducible by the viewer | The audit panel's glance-fact count, scroll ratio |
| **Designer heuristic** | A threshold you set yourself, not derived from a study — must say so explicitly | "We capped it at 3, our own budget, not a literature number" |
| **Fabricated example** | Synthetic data used to demonstrate the UI, never presented as real | Omar Al-Hassan's account balances |

A number with no tag is the failure mode the product lead flagged. Every number in the final copy must carry one.

## 2. Contrast audit — fails found, fixed

Ran actual WCAG relative-luminance contrast math (not a visual guess) against every color pair in `cleargrid-design.md`. The doc's existing claim — "tested contrast: passes AA on white for large text/icons" — undersells the problem: it reads as a general pass, but four colors fail normal-text AA (4.5:1) and only clear the large-text/UI threshold (3:1).

| Pair | Ratio | Normal text AA (4.5) | Large/UI AA (3.0) |
|---|---|---|---|
| Teal `#069494` on white | 3.70 | FAIL | pass |
| Coral `#DC4A3E` on white | 4.12 | FAIL | pass |
| Coral on coral-wash (badge default) | 3.66 | FAIL | pass |
| Success green `#1E8E5A` on white | 4.14 | FAIL | pass |
| Warning amber `#B8790A` on white | 3.63 | FAIL | pass |
| Text-muted `#8A9094` on page background | 3.04 | FAIL | pass |
| Teal-deep `#04716D` on white | 5.85 | pass | pass |
| Text-secondary `#5B6166` on white/bg | 5.90–6.28 | pass | pass |
| Text-primary `#0A0A08` on white | 19.81 | pass | pass |

**Rule going forward, not just for this page**: teal-deep, not teal, for any text under 18px regular / 14px bold. Coral, green, and amber the same — they're fine for large badges/icons/status dots but not for anything readable as body text.

**Darkened values that clear 4.5:1 on white, same hue, for use wherever these colors carry actual text** (computed, not eyeballed):

| Token | Original | Corrected for text use |
|---|---|---|
| `--accent-coral-text` | `#DC4A3E` | `#D93D30` |
| `--accent-success-text` | `#1E8E5A` | `#1D8756` |
| `--accent-warning-text` | `#B8790A` | `#A36B09` |
| `--text-muted` (if used as readable copy, not just a dash) | `#8A9094` | `#71787C` |

Add these as separate `-text` tokens rather than replacing the originals — the original lighter values are still correct for large icons, badge backgrounds, and chart fills, where 3:1 is the right bar. Two tokens per color, each used for its correct size class, is the actual fix. One token used everywhere was the bug.

## 3. The "3" problem — thresholds stated as if derived, not chosen

This is the sharpest form of the product lead's critique, and it shows up twice in the existing work.

**In `dense-ui-design-guide.md` §5.2**: "Cap the salience budget. At most three attention-grabbing elements visible at once." The alert-fatigue literature cited elsewhere in that document (Ancker et al., override rates 49–96%) supports *capping* alerts. It does not say the number is three. As written, this reads like a research-derived number. It isn't — it's a designer's working budget.

**In `cleargrid-borrower-profile-v3.html`'s audit panel**: `alerts<=3` (good), `alerts<=5` (mid), `clicks<=4` (good), `clicks<=9` (mid), `scroll<=1.02` (good), `scroll<=1.3` (mid). None of these thresholds are sourced. They're reasonable, but "reasonable" isn't what was asked for.

**The fix isn't to remove the thresholds — it's to say where they actually come from:**

| Threshold | Honest derivation |
|---|---|
| ≤3 coral/alert elements | Cowan's working-memory reanalysis puts real capacity near 4 chunks (cited in the same document). Reserve one chunk of that budget for the live conversation itself — the borrower talking — leaving 3 as the interface's share. State it exactly this way in the case study: a derived budget, not a magic number. |
| ≤4 clicks to reach any brief-mandated data point | Matches the same 4-chunk model: each click represents committing a new chunk to working memory mid-task. Cap the interface's click cost at the same ceiling as its visual chunk cost, for internal consistency. |
| ≤1.3× viewport scroll (mid), ≤1.02× (good) | This one has no defensible derivation and should be labeled a **designer heuristic**, plainly, in the case study: "an internal target, not a literature number — chosen so the page fits in roughly one screen of scroll for a fast glance-mode read." Don't dress it up as more than that. |

This is the actual move the product lead is asking for: not zero heuristics, but *stating* which numbers are derived and which are chosen, instead of letting both sit at the same confidence level in the prose.

## 4. Decision ledger — existing choices, checked

Most of the existing reasoning (`dense-ui-design-guide.md`, `cleargrid-design-assumptions.md`) is already unusually well-cited for a design case study — better than most of what's in the design-portfolio literature reviewed earlier. This ledger converts the strongest ones into the four-field format for direct use in the case study, and flags the two that need a confidence downgrade stated openly.

| Decision | Evidence | Alternative rejected | Confidence |
|---|---|---|---|
| Full mirrored RTL frame, not side-by-side bilingual fields | Checked ClearGrid's own side-by-side pattern (AI Voice transcript view) against outside precedent (enterprise BI tools, UAE gov portals, Arabic-UX guidance) — none support side-by-side for a dense grid screen specifically | Side-by-side, initially the working assumption, dropped after the precedent check | High — this is the strongest-documented decision in the project; use it as the case study's flagship "we checked our first instinct" example |
| Escalation-reason line as a new header-level field | ClearGrid's own site states six borrower states drive routing (dispute, hardship, etc.); none of the four production screenshots surface this despite `Disputed: No` existing as a buried field | Leaving it in Custom Attributes as-is | Medium — flagged explicitly as a possible data-model gap, not just a UI gap, in the original research. Keep that caveat in the case study; don't upgrade it to certainty it doesn't have. |
| Inline labels over stacked labels (labels beside values, not above) | Salesforce's own published figure: 30% density gain (developer blog) vs. a third-party measurement of ~40% (cited separately, not conflated) | Keeping the current stacked-label pattern | High — both source numbers are named and separated, not merged into one unsourced "30-40%" claim. Keep that separation in the case study copy. |
| One alert color (coral) for "needs attention," used nowhere else on the page | Preattentive conjunction-search literature (Healey): once color, size, and weight all encode urgency simultaneously, none of them pop individually | Multi-attribute urgency encoding (color + size + weight all together), which is what the original screen effectively had via inconsistency | High |
| Fixed field order in the account column, no accordions for brief-mandated data | Nielsen's response-time thresholds (0.1s / 1s) — an accordion expand plus reflow mid-call exceeds both | Keeping the original accordion pattern for Custom Attributes / Broken Promises / Timeline | High |
| Western numerals in the Arabic build | Direct observation of ClearGrid's own live `/ar/` site, cross-checked against UAE/KSA fintech convention | Eastern Arabic-Indic numerals (also linguistically valid, but not what ClearGrid itself uses) | Medium — single-source observation of one live site; say so, don't imply this was tested with users |

| Contrast ratios (3.70, 4.12, 5.85, etc.) | Live-computed | Computed directly from the published hex values via the WCAG relative-luminance formula, reproducible by anyone — cite the formula, not a tool name, since the math itself is the source |

| Alert-override rates 49–96% (clinical literature) | External fact | Ancker et al., BMC Medical Informatics — used as directional support for capping alerts, not as a claim about this specific interface |

## 6. What to physically add to the case study build

- A visible **"Decisions & Evidence"** section or expandable appendix using the table in §4 — this is the section a sharp interviewer reads first on a second look, and it's currently implicit in your source docs rather than surfaced in the case study itself.
- A **metric footnote/appendix** using §5 — even a compact version (5–6 rows) signals the discipline the product lead asked for without turning the main narrative into a citations page.
- The **corrected `-text` color tokens** from §2, applied everywhere coral/green/amber text renders below 18px.
- One explicit sentence near the audit-panel embed in the prototype: state which of its live thresholds are literature-derived and which are your own working targets (§3). This turns a cute feature into exactly the kind of self-aware, accountable design artifact that answers the original critique directly, inside the product itself, not just in the write-up around it.

## 7. One thing to say to the interviewer, if it comes up again

If asked how this round differs from the first: "The first version was internally consistent. This version is externally checked — every color was run through the actual contrast formula, every claimed research-backed threshold was traced back to what the research actually supports versus what I chose myself, and every number in the write-up is tagged by source." That is a direct, factual answer to the specific feedback given, not a defensive one.
